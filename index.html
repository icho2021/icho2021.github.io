SoloData governance

CanadaBuys Data Quality & Compliance Agent↗

Python, DuckDB, AWS Batch

Canada publishes every contract its central buying department awards. Anyone can download it; almost nobody can safely use it. This answers one question: which rows can be used as they are, and which need a person first.

Full breakdown →

Four ways to handle a problem, and deleting is not one of them. 21 rules, each tagged by what it triggers: stop the batch, label the row for a person, fix it mechanically after approval, or just count it. 650,571 cases the government documentation already explains stay out of the findings table, so they do not bury the 126,708 that matter.

A rule that finds nothing and a rule that is quietly broken look identical in the output. So each control has a test that breaks it on purpose and asserts exactly the right alarm fires. Writing those tests exposed two mistakes in my own design, including a test that never reached the check it was meant to cover.

Never overwriting a batch paid off. The second monthly file restated 13,218 already-published records, and one disappeared from the public record entirely. Had each run replaced the last, none of it would be visible.

The language model never decides anything. It finds the official paragraph behind a rule and quotes it; the quote is then checked against the source text and rejected when it does not appear. It invented one claim, the check caught it, and nothing downstream moved.

Same answer on AWS as on my laptop, to the digit. 124 seconds on Batch with Fargate, then torn down, including the resources that quietly keep billing.

Next: put the monthly run on a schedule with an alarm when it fails, wire the fault-injection suite into CI so it runs on every commit, and add freshness rules so the pipeline also answers whether the data is current, not only whether it is correct.

Python · DuckDB · Parquet · Docker · AWS Batch on Fargate · S3 · ECR · CloudWatch · Ollama (local inference)

Team projectCloud

QuickScan Hub↗

My part was the failure path and the Terraform

A cloud security scanning platform on AWS, defined in Terraform. Scans run asynchronously through a queue instead of inline, so a slow scan never holds a request open.

Full breakdown →

Request → SQS → worker long-polling → scanner on Fargate → report to S3 → served back through the API. Workers scale on queue depth rather than CPU, because queue depth is what actually measures the backlog.

The network sits in three tiers. The scanners have no inbound route at all and reach AWS services through a Gateway Endpoint. Subnets span two availability zones so the load balancer can reroute and ECS health checks can replace a task.

What I verified myself was the failure path: a deliberate dead-letter-queue injection test, confirming that a failing message routes to the DLQ and the CloudWatch alarm fires. Terraform is split by resource so each piece reads on its own.

Scope: 34 requests total, peak CPU 0.77%, peak queue depth around 9. This validated failure handling, not throughput. The distributed architecture was the team's design; I do not present it as mine alone.

AWS ECS Fargate · SQS · S3 · DynamoDB · ALB · NAT · VPC Gateway Endpoint · CloudWatch · Terraform · NGINX

SoloModelling

E-Commerce Analytics Platform↗

Star schema with a frozen metric layer

Six tables and one file that stops two correct queries from producing two different numbers.

Full breakdown →

Two fact tables and four dimensions. The facts are deliberately split by grain, one row per order and one per order line, because collapsing them silently doubles revenue on any multi-item order.

A quality suite runs on every load: required fields non-null, primary keys unique across the fact table and all four dimensions, composite keys unique, amounts non-negative, source freshness, and orphaned foreign keys. Each check is marked critical or not, so a failure either stops the load or is simply recorded.

The part I would keep in any project is the metrics file. GMV, average order value, repeat rate and on-time delivery each have their definition and filters written down, including that the default excludes anything not yet delivered. Without it, two people write two correct queries and get two different answers.

Python · DuckDB · Parquet · S3 (raw and processed zones) · run metadata per load

SoloApplied AI

Adaptive Hint Agent↗

Local LLM behind a rule-based policy

Reads how someone is struggling from their interaction logs, then decides what kind of hint that calls for before generating anything.

Full breakdown →

Four stages: features from interaction logs, rule-based inference of the learner's current state, a policy that decides what feedback that state calls for, and only then generation.

Deciding which hint to give stays in the rules, not the prompt, so the decision can be inspected and changed without re-tuning a model. The model runs locally through Ollama behind a provider abstraction, so the same pipeline can point at a local or hosted backend without the rest of the code knowing which.

To tell whether the adaptive policy was actually better, I built a trace-replay harness that runs the same recorded learner sessions through three policies — fixed rules, data-driven, and adaptive — and scores each on responsiveness, hint effectiveness, efficiency, frequency and recovery. Comparing policies on identical traces is the only way the comparison means anything.

Agent behaviour is defined in an instruction file kept separate from the code, so changing how it responds is an edit to that file and a re-run of the harness rather than a code change.

Python · Ollama · local LLM · feature engineering · prompt design · provider abstraction layer

SoloFull stack

Capybara Comfort Shop↗

The bug that changed how I debug

A full-stack store where uploaded images kept vanishing after every deploy. The fix mattered less than how I found it.

Full breakdown →

I tried several candidate fixes in the upload code and none worked, because the fault was not in any one place: files were written to the container's own disk, and that filesystem is wiped on redeploy.

I found it by giving up on single-point fixes and walking the whole request path by hand, from the browser upload through the API to the database write and into the deployment environment.

My fix was a stopgap and I wrote that in the README at the time: object storage is the real answer. Recording the shortcut was the point, not hiding it.

React · Node.js / Express · PostgreSQL · Render

SoloJava

Virtual Pet Management System↗

Java desktop application

A state machine for the pet's needs and mood, written to an MVC brief with the model kept testable on its own.

Full breakdown →

The model carries no Swing dependency, so the behaviour can be unit tested without constructing any interface. Separation of concerns held to strictly rather than approximately, which is easy to claim and easy to check by trying to instantiate the model on its own.

Several pet personalities share most of their behaviour, so the common parts live in interfaces and abstract classes and each personality supplies only what differs. Writing the second personality is what shows whether the first one was factored properly.

JUnit tests cover the state transitions, the boundary conditions where a need crosses its threshold, and each personality strategy — the three places where a state machine actually breaks.

Java · Swing · MVC · JUnit
